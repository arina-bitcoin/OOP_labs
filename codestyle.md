# Требования к лабораторным работам по C++

Основой служит [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html). Правила этого документа уточняют и местами переопределяют его: используем отступ в 4 пробела, строку до 120 символов, заголовки `.hpp` с `#pragma once` и описанный ниже порядок инклюдов.

Для форматирования используем **clang-format** и файл `.clang-format` в корне проекта. **clang-tidy** — инструмент статического анализа; он дополняет форматирование, но не заменяет его.

Требования конкретной лабораторной к интерфейсам, стандарту языка и разрешённым средствам C++ имеют приоритет. По умолчанию используем C++20. В материалах лабораторной № 1 указан C++17 и предусмотрены ограничения на контейнеры, классы и умные указатели: это условия конкретной работы, а не общий запрет для всего курса.

## 1. Структура проекта и сборка

**В корне каждой лабораторной обязательны `include/`, `src/`, `test/` и `CMakeLists.txt`.**

```text
lab_01/
├── CMakeLists.txt
├── .clang-format
├── .gitignore
├── README.md
├── include/
│   └── lab01/
│       ├── array_ops.hpp
│       └── funcs.hpp
├── src/
│   ├── main.cpp
│   ├── array_ops.cpp
│   └── funcs.cpp
├── test/
│   ├── array_ops_test.cpp
│   └── funcs_test.cpp
└── build/                  # создаётся при сборке, не хранится в репозитории
```

- `include/` содержит заголовки с интерфейсами. Подкаталог `lab01/` задаёт уникальный префикс проекта и предотвращает конфликты имён заголовков.
- `src/` содержит реализацию `.cpp`, включая `main.cpp`. Ввод, вывод и меню отделяем от вычислений и операций над данными, чтобы последние можно было вызвать из тестов.
- `test/` содержит тесты Google Test. Используем имя `<имя_модуля>_test.cpp`; структура подкаталогов при необходимости повторяет структуру модулей. Название каталога — именно `test/`.
- Корневой `CMakeLists.txt` описывает библиотеку с логикой, исполняемую программу и отдельную цель с тестами. Программа и тесты связываются с одной библиотекой; `main.cpp` программы не входит в тестовую цель.
- Файлы сборки и скачанные зависимости располагаются в `build/`. Добавляем `/build/` в `.gitignore`; сгенерированные объектные файлы и исполняемые файлы не сдаём вместо исходников.

### Сборка через CMake

**ASan обязателен всегда**: для программы, библиотеки и тестов, в `Debug`, `Release` и остальных конфигурациях. Флага для его отключения нет. Для отладки выбираем `Debug`.

`CMakeLists.txt` описывает, какие файлы нужно собрать и какие библиотеки связать. В примере три цели: `lab01_lib` — общая логика, `lab01_main` — программа с меню, `tests` — тесты этой же логики.

```cmake
# 1. Название проекта и стандарт языка.
cmake_minimum_required(VERSION 3.20)
project(lab01 LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# 2. Используем GNU GCC. ASan включён для всех собираемых исходников.
if(NOT CMAKE_CXX_COMPILER_ID STREQUAL "GNU")
    message(FATAL_ERROR "Use GNU GCC: configure with -DCMAKE_CXX_COMPILER=g++")
endif()
add_compile_options(-Wall -Wextra -Wpedantic -g -fsanitize=address -fno-omit-frame-pointer)
add_link_options(-fsanitize=address)

# 3. Ищем Google Test; если он не установлен — скачиваем фиксированную версию.
find_package(GTest QUIET)
if(NOT GTest_FOUND)
    include(FetchContent)
    FetchContent_Declare(
        googletest
        GIT_REPOSITORY https://github.com/google/googletest.git
        GIT_TAG v1.15.2
    )
    FetchContent_MakeAvailable(googletest)
endif()

# 4. Собираем общую логику и указываем каталог заголовков.
add_library(lab01_lib src/array_ops.cpp src/funcs.cpp)
target_include_directories(lab01_lib PUBLIC include)

# 5. Собираем программу и связываем её с общей логикой.
add_executable(lab01_main src/main.cpp)
target_link_libraries(lab01_main PRIVATE lab01_lib)

# 6. Собираем тесты и регистрируем их запуск в CTest.
add_executable(tests test/array_ops_test.cpp test/funcs_test.cpp)
target_link_libraries(tests PRIVATE lab01_lib GTest::gtest_main)
enable_testing()
add_test(NAME Lab01Tests COMMAND tests)
```
### Обязательные флаги ASan

AddressSanitizer проверяет обращения к памяти во время работы программы. Он помогает обнаруживать выход за границы выделенной памяти, обращение после освобождения и двойное освобождение.

| Флаг GCC | Назначение |
| --- | --- |
| `-fsanitize=address` | Включает ASan; нужен и при компиляции, и при линковке |
| `-g` | Добавляет отладочную информацию для диагностики |
| `-fno-omit-frame-pointer` | Помогает получить понятный стек вызовов |
| `-Wall -Wextra -Wpedantic` | Включает предупреждения компилятора; это отдельные проверки, не ASan |
## 2. Заголовки и порядок `#include`

### Самодостаточность и пути

- Каждый заголовок начинается с `#pragma once` и компилируется при самостоятельном подключении. Include guards через `#ifndef` в собственных заголовках не используем.
- Каждый файл явно подключает заголовки используемых им типов и функций. Не полагаемся на случайные транзитивные зависимости. Парный заголовок уже предоставляет собственные объявления — повторно объявлять их в `.cpp` не нужно.
- Зависимости, нужные только реализации, подключаем в `.cpp`. Допустимые предварительные объявления используем, когда полного определения типа не требуется; типы стандартной библиотеки самостоятельно не объявляем.
- Собственные заголовки подключаем в кавычках относительно корня `include/`: `#include "lab01/array_ops.hpp"`. Стандартные, системные и сторонние заголовки — через `<...>`.
- В `#include` запрещены абсолютные пути и компоненты `.` / `..`: нельзя `"../include/lab01/array_ops.hpp"`, `"./array_ops.hpp"` или `"/home/user/project/..."`. Путь `"lab01/array_ops.hpp"` допустим: это путь относительно настроенного include-каталога, а не перемещение по каталогам от исходного файла.
- Не включаем `.cpp` и агрегирующие нестандартные заголовки вроде `<bits/stdc++.h>`.

### Группы инклюдов

В начале файла располагаем следующие группы, **строго в указанном порядке**, с одной пустой строкой между непустыми группами:

1. **Один парный заголовок**: в `array_ops.cpp` — `"lab01/array_ops.hpp"`; в `array_ops_test.cpp` — тот же заголовок проверяемого модуля. Он идёт первым, чтобы другие инклюды не скрывали недостающие зависимости в нём. В заголовочных файлах и в `main.cpp` без парного заголовка эту группу пропускаем.
2. **Заголовки C и операционной системы**: `<stdio.h>`, `<sys/types.h>`, `<unistd.h>`. В переносимом C++ предпочитаем доступные C++-обёртки, например `<cstdio>` и `<cstddef>`; они относятся к следующей группе.
3. **Стандартная библиотека C++**: `<algorithm>`, `<cstddef>`, `<iostream>`, `<string>`, `<vector>`.
4. **Сторонние библиотеки и библиотеки других проектов**: `<boost/...>`, `<fmt/format.h>`, `<gtest/gtest.h>`. Это одна группа; принадлежность зависимости другой команде или репозиторию не создаёт дополнительную группу.
5. **Остальные заголовки текущего проекта** в кавычках.

Внутри каждой группы сортируем полные пути лексикографически, с учётом регистра. Удаляем дубли и неиспользуемые инклюды. Не добавляем пустые группы или неиспользуемые зависимости ради соблюдения схемы.

Например, порядок инклюдов в `array_ops_test.cpp`, если все перечисленные зависимости действительно нужны:

```cpp
#include "lab01/array_ops.hpp"

#include <sys/types.h>

#include <algorithm>
#include <cstddef>
#include <vector>

#include <gtest/gtest.h>

#include "lab01/funcs.hpp"
```

Это локальная договорённость на основе [порядка инклюдов Google](https://google.github.io/styleguide/cppguide.html#Names_and_Order_of_Includes). В частности, сторонний `<gtest/gtest.h>` остаётся в группе сторонних библиотек, несмотря на расширение `.h`.

## 3. Имена и пространства имён

1. Классы, структуры, перечисления и функции именуем в `CamelCase`: `ArrayStorage`, `FindMax`. Геттеры и сеттеры можно именовать как переменные: `size()`, `set_size()`.
2. Переменные и параметры — `snake_case`: `out_value`, `element_count`; поля класса — с завершающим `_`: `size_`. Имена констант — `kCamelCase`: `kMaxSize`. Имена файлов — `snake_case.hpp` и `snake_case.cpp`.
3. Выбираем содержательные имена; краткие `i` и `j` допустимы для локальных индексов. Если задание фиксирует имя функции, сохраняем его для совместимости с проверкой.
4. `using namespace` запрещён, в том числе в `.cpp` и тестах. Для длинного пространства имён допустим псевдоним: `namespace mongo = service_name::models::mongo;`.
5. Код проекта помещаем в одноимённое пространство имён: для `lab01` — `namespace lab01`. Вложенным каталогам заголовков соответствуют вложенные пространства: `include/lab01/models/item.hpp` — `lab01::models`. Каталоги `include/`, `src/`, `test/` в имя пространства не входят. `main` остаётся в глобальном пространстве имён.
6. Вспомогательные функции, классы и константы, используемые только в одном `.cpp`, помещаем в анонимное пространство имён. В заголовках анонимные пространства имён не используем. Если такой блок разрастается до сотен строк, выделяем самостоятельный модуль с парой `.hpp` / `.cpp`.

## 4. Общие правила C++

1. По возможности определения функций и методов размещаем в `.cpp`, а объявления — в `.hpp`. Шаблоны и необходимые `inline` / `constexpr`-определения могут находиться в заголовках. Не определяем там обычные функции и изменяемые глобальные переменные с внешним связыванием: это может нарушить ODR при подключении из нескольких единиц трансляции.
2. Инициализируем переменные до чтения. Для скалярных значений предпочитаем `{}`, особенно для предотвращения сужения. Для классов и контейнеров учитываем различия между конструкторами с `()` и списком инициализации.
3. Неизменяемые локальные переменные и входные ссылки/указатели делаем `const`; методы, не меняющие наблюдаемое состояние объекта, также объявляем `const`. Выходные параметры остаются изменяемыми. Поля делаем `const`, если неизменяемость входит в модель класса и не ломает нужные операции копирования или присваивания.
4. Для констант времени компиляции используем `constexpr`, а не `#define`. Если одна строковая константа используется более двух раз, выносим её в именованную константу. Для одного `.cpp` — в анонимное пространство имён; для нескольких файлов — в тематический `names.hpp`, например как `inline constexpr` в пространстве имён проекта.
5. `auto` используем, когда тип очевиден из правой части или его явная запись мешает чтению. Не скрываем им значимые различия типов, ссылок и владения.
6. Если параметр обозначает обязательный одиночный объект, используем ссылку вместо потенциально нулевого указателя. Это правило не заменяет указатель на массив ссылкой на первый элемент: для массива учитываем размер и контракт, включая допустимость `nullptr` при нулевом размере.
7. Не смешиваем ввод/вывод с вычислениями. Результаты возвращаем через `return`; выходные параметры используем, если они предусмотрены интерфейсом. Документируем, что происходит с ними при неуспехе, и проверяем признак успеха до чтения результата.
8. Управление ресурсами строим на RAII, где это разрешено заданием. При обязательной ручной работе с памятью явно определяем владельца, согласуем `new` / `delete` и `new[]` / `delete[]`, освобождаем память на всех путях выхода. Не допускаем утечек, двойного освобождения и обращений за границы.
9. Метод, которому не нужно состояние объекта и виртуальное переопределение, делаем `static` или свободной функцией. Класс только со статическими методами заменяем пространством имён.
10. Переопределение виртуального метода помечаем `override` или `final`. Не бросаем исключения из деструкторов.
11. Исключения используем для ошибок, а не обычного ветвления. Ловим конкретные типы по `const`-ссылке. `catch (...)` допустим только с дальнейшим `throw;`; для освобождения ресурсов предпочитаем RAII.
12. В лямбдах не используем общий захват по ссылке `[&]`; перечисляем необходимые захваты явно и следим за временем жизни объектов.
13. Для `switch` по перечислению с фиксированным набором значений перечисляем все варианты и не добавляем `default`, чтобы компилятор мог указать на новый необработанный вариант. Внешние числовые значения проверяем до преобразования в перечисление.
14. Удаляем мёртвый код и закомментированные старые реализации. Комментарий объясняет причину решения, ограничения или контракт, а не пересказывает очевидную строку.

## 5. Форматирование

- Отступ — 4 пробела, табуляции не используем. Базовый отступ продолжения строки — 4 пробела. Целевая максимальная длина строки — 120 символов; длинные неделимые строки и пути проверяем вручную.
- Фигурная скобка функции, класса и однострочного условия стоит на той же строке. Для управляющего условия, перенесённого на несколько строк, открывающая скобка выносится на отдельную строку.
- У `if`, `else`, `for`, `while`, `do` обязательны фигурные скобки, даже для одного оператора. Непустые тела функций и управляющих конструкций не записываем целиком в одну строку.
- Указатель и ссылка примыкают к типу: `const int* data`, `int& out_value`. Объявляем по одной переменной за раз.
- Если параметры или аргументы не помещаются в строку, форматтер раскладывает их по одному на строку. Не подгоняем выравнивание вручную.
- Тело `namespace` не получает дополнительного отступа. `public:`, `protected:`, `private:` выравниваются с объявлением класса.
- Не оставляем пробелы в конце строк; файл завершаем переводом строки. Между логическими блоками достаточно одной пустой строки.

### Применение `.clang-format`

Положите приложенный `.clang-format` рядом с корневым `CMakeLists.txt`.

```sh
# Отформатировать только собственный код.
find include src test -type f \( -name '*.hpp' -o -name '*.cpp' \) \
    -exec clang-format -i --style=file {} +

# Проверить форматирование без изменения файлов.
find include src test -type f \( -name '*.hpp' -o -name '*.cpp' \) \
    -exec clang-format --dry-run --Werror --style=file {} +
```

## 6. Общие правила тестирования

1. Каждая лабораторная содержит автоматические тесты Google Test в `test/`. Ручной запуск меню дополняет их, но не заменяет. Тестируем ту же реализацию, с которой собирается программа: не копируем алгоритмы в тестовые файлы.
2. Тест проверяет **поведение и контракт**: возвращаемое значение, изменения данных и выходных параметров, ожидаемую ошибку. Не привязываем его к частным деталям реализации без необходимости.
3. Покрываем обычные сценарии, граничные значения и предусмотренные контрактом ошибки. Для структур данных это могут быть пустая структура, один элемент, первая/последняя позиция, отсутствие результата, повторы и изменение размера; для строк — также завершающий `\0`, для матриц — размеры и содержимое. Недопустимый вход передаём только если интерфейс определяет его обработку, а не требует его отсутствия как предусловие.
4. Один тест — один понятный сценарий; в нём может быть несколько связанных проверок. Имена описывают поведение: `TEST(FindMaxTest_Fail, EmptyInputReturnsFalse)`, а не `Test1`. Основные имена наборов и сценариев пишем в `CamelCase`. Подчёркивание используем только как разделитель перед суффиксом, показывающим особенность набора, например `_Death`, `_Throw` или `_Fail`. Проверки завершения процесса, исключений и отказов группируем в отдельные наборы с суффиксами по правилам ниже.
5. Строим тест по схеме «подготовка данных — действие — проверка». Ожидаемый результат задаём независимо: не вычисляем его той же функцией или копией проверяемого алгоритма.
6. Каждый тест создаёт собственные данные и не зависит от порядка запуска, изменений глобального состояния, сети, текущего времени или нефиксированной случайности. Если нужны файлы, используем отдельное временное окружение и очищаем его.
7. Используем `EXPECT_*` для независимых проверок и `ASSERT_*`, если после неуспеха нельзя безопасно продолжать текущую функцию теста. Например, сначала проверяем успех поиска, затем значение выходного параметра. Для C-строк сравниваем содержимое через `EXPECT_STREQ`; для вещественных результатов выбираем подходящую проверку, например `EXPECT_NEAR` с обоснованной погрешностью. См. [GoogleTest Primer](https://google.github.io/googletest/primer.html).
8. Освобождаем ресурсы и при провале проверки. Учитываем, что `ASSERT_*` прерывает текущую функцию и может пропустить следующий за ним `delete[]`. Общую подготовку и очистку выносим в fixture с `SetUp` / `TearDown` или используем RAII там, где это разрешено заданием.
9. Для исправленного дефекта добавляем регрессионный тест, который воспроизводит ошибку. Новое поведение сопровождаем проверкой соответствующего сценария.
10. Не маскируем ошибки отключением теста, удалением проверок или изменением ожидаемого значения без изменения требований. Успешный запуск с нулём найденных тестов не принимается.
11. Перед сдачей собираем и запускаем программу и CTest с обязательным ASan по инструкциям раздела 1. Это относится ко всем работам, а не только к задачам с ручным управлением памятью. Отдельно учитываем доступность проверки утечек. Прохождение функциональных тестов само по себе не доказывает отсутствие ошибок памяти.

### Группировка тестов: суффикс в первом аргументе

В `TEST(ИмяНабора, ИмяСценария)` **первый аргумент задаёт группу тест-кейсов**, второй — конкретный сценарий. Обязательный суффикс ставим **в конце первого аргумента**. Во втором аргументе его не повторяем.

| Тип набора | Суффикс первого аргумента | Пример |
| --- | --- | --- |
| Обычные успешные сценарии | **`Test`** | `TEST(FindMaxTest, NonEmptyInputWritesMaximum)` |
| Ожидаемое завершение процесса: `EXPECT_DEATH` / `ASSERT_DEATH` | **`_Death`** | `TEST(AllocatorTest_Death, CorruptedState)` |
| Ожидаемое исключение: `EXPECT_THROW` / `ASSERT_THROW` | **`_Throw`** | `TEST(ArrayOpsTest_Throw, InvalidIndex)` |
| Ожидаемый отказ без исключения: код ошибки, `false`, `nullptr` | **`_Fail`** | `TEST(FindMaxTest_Fail, EmptyInputReturnsFalse)` |

Все проверки одного модуля с одинаковым типом исхода объединяем одним первым аргументом: например, `TEST(ArrayOpsTest_Throw, InvalidIndex)` и `TEST(ArrayOpsTest_Throw, InvalidSize)` входят в общий набор `ArrayOpsTest_Throw`. Не смешиваем обычные, death-, exception- и fail-сценарии в одном наборе. К базовому имени набора добавляем ровно один суффикс: `ArrayOpsTest_Throw`, а не `ArrayOpsTest_Throw_Fail`.

Для `TEST_F` и `TEST_P` правило такое же: соответствующий суффикс получает имя fixture в первом аргументе. Общую подготовку можно сохранить в базовой fixture и создать от неё отдельные fixtures или псевдонимы с нужными именами.

Тип набора определяется смыслом сценария, а не названием assertion: например, `EXPECT_FALSE(IsEmpty())` для непустого контейнера относится к обычному `Test`. `_Fail` нужен, когда проверяемая операция должна сообщить о неуспехе.

Все эти тесты должны **проходить**, когда ожидаемый исход подтверждён. `_Fail` не разрешает оставлять падающие тесты: не добавляем `FAIL()` ради имени набора и не используем `WILL_FAIL` в CTest. Отсутствие ожидаемого исключения, завершения или отказа должно приводить к провалу проверки.

Пример для контракта `FindMax`: пустой диапазон даёт `false`, непустой — `true` и максимум через `out_value`. Конкретные имена из задания при необходимости сохраняем.

```cpp
#include "lab01/funcs.hpp"

#include <gtest/gtest.h>

namespace lab01 {
namespace {

TEST(FindMaxTest, NonEmptyInputWritesMaximum) {
    const int data[]{3, 9, 4, 1};
    int value{};

    const bool found = FindMax(data, 4, value);

    ASSERT_TRUE(found);
    EXPECT_EQ(value, 9);
}

TEST(FindMaxTest_Fail, EmptyInputReturnsFalse) {
    int value{};

    EXPECT_FALSE(FindMax(nullptr, 0, value));
}

}  // namespace
}  // namespace lab01
```

Во втором тесте значение `value` после неуспеха не проверяется: пример не задаёт такого обещания. Если интерфейс гарантирует сохранение выходного параметра, добавляем проверку этого условия.
